# The data model

Everything lives in one Supabase Postgres database, but that database has two halves that were designed independently and have never been reconciled. One half is Supabase-native: `profiles` plus roughly sixty tables keyed on the `auth.users` uuid, reached through the Supabase JS client and governed by Row Level Security. The other half is Prisma-managed: 35 models keyed on a cuid, reached through the Prisma client over a plain Postgres connection that RLS does not constrain. The same person exists in both halves under two different primary keys, and confusing the two is the defect this codebase produces most often. This chapter says which table sits in which key space, what actually writes each one, and where the schema on disk does not match the schema in the database.

## The two key spaces

A signed-in person has two identifiers:

|                    | Supabase identity                                                                                                                | Prisma identity                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Primary key        | `auth.users.id`, mirrored as `profiles.id`                                                                                       | `User.id`                                                                  |
| Type               | `uuid`                                                                                                                           | `cuid` (a `String`, e.g. `cl9x…`)                                          |
| Created by         | Supabase Auth on signup, always                                                                                                  | only by the code in [`src/lib/identity/`](../../src/lib/identity/), rarely |
| Reached via        | `createServerSupabaseClient()` / `createServiceRoleClient()` in [`src/lib/supabase/server.ts`](../../src/lib/supabase/server.ts) | `prisma` from [`src/lib/prisma.ts`](../../src/lib/prisma.ts)               |
| Constrained by RLS | yes for the session client, no for the service role                                                                              | no                                                                         |

Most accounts have only the first. The header of [`src/lib/identity/projection.ts`](../../src/lib/identity/projection.ts) records the measurement that started the identity work: 200 Supabase auth users, 200 `profiles` rows, 8 rows in the Prisma `User` table. Email confirmation is on, so signup produces no session, so `/api/auth/register` never ran for about 96% of accounts and no Prisma row was written. Three subsystems key on `User.id` while every caller holds a uuid, so for those accounts the consent ledger could not be written, erasure matched nothing, and the AI decision log silently dropped rows.

The bridge is [`src/lib/identity/`](../../src/lib/identity/) and nothing else:

- `requirePrismaUserId(supabaseUserId)` resolves the uuid to a cuid, creating a projection row if there is none. It throws, so gates fail closed.
- `tryPrismaUserId()` is the read-path form; it returns `null` instead of throwing.
- `projectSupabaseUser()` is the only function permitted to create or adopt a `User` row. A projection is deliberately never permissive: no `Consent` row, no `parentId`, no `Subscription`, no invented date of birth. Read the comment block at [`projection.ts:19-40`](../../src/lib/identity/projection.ts) before touching it.
- [`src/__tests__/identity-guard.test.ts:37`](../../src/__tests__/identity-guard.test.ts) fails the suite on a `User` row created outside that module. `app/api/auth/register/route.ts` and `app/api/auth/teacher-signup/route.ts` are explicitly allowlisted, so there are three legitimate creation sites, not one.

`User.dateOfBirth` and `User.country` are nullable ([`prisma/schema.prisma:162`](../../prisma/schema.prisma)). They used to be NOT NULL, which forced the 2026-04-20 backfill to invent `2000-01-01` and `GB`. That computed to age 26, wrote `isMinor: false`, and switched the parental-consent gate off for children. NULL is the honest value; do not restore the constraint and do not substitute a default anywhere a consumer renders it.

The `subscription_status` / `ielts_status` split is the shape to copy for any future entitlement. Do not overload `subscription_status` again: it is a single text field and a person can hold more than one live subscription.

### Which key each table is on

| Key space                                 | Tables                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supabase uuid (`auth.users` / `profiles`) | `profiles`, `enrolments`, `module_progress`, `assessment_attempts`, `certificates`, `practice_sessions`, `quiz_responses`, `school_members.user_id`, `class_students.student_id`, `analytics_snapshots.student_id`, `school_students`, `parental_consents.student_user_id`, `human_review_requests.user_id`, `marking_submissions.student_id`, `markers.user_id`, `teacher_moderations.reviewer_user_id`, `affiliate_accounts.user_id`, `affiliate_conversions.referred_user_id`, `import_results.user_id`, `bulk_import_jobs.created_by` |
| Prisma cuid (`User.id`)                   | every FK in [`prisma/schema.prisma`](../../prisma/schema.prisma) except the one below, plus `progress_poems` / `progress_games` / `progress_quizzes` / `progress_reading_age` / `progress_cefr`, whose `user_id` is TEXT and whose RLS calls `app_user_id()`                                                                                                                                                                                                                                                                              |
| Deliberate hybrid                         | `MarkingSubmission.studentId` is the Supabase uuid, and its Prisma relation points at `User.supabaseUserId` rather than `User.id` ([`prisma/schema.prisma:870`](../../prisma/schema.prisma))                                                                                                                                                                                                                                                                                                                                              |
| Neither                                   | `free_allowance_usage.subject_key` (uuid _or_ an IP digest), `rate_limit_counter.bucket_key` (a salted hash), `courses.id` / `modules.id` (hand-written TEXT slugs)                                                                                                                                                                                                                                                                                                                                                                       |

Two exceptions are load-bearing and must not be "tidied":

1. **`parental_consents.student_user_id` is the Supabase uuid on purpose.** It has a foreign key to `profiles(id)`, and `hasApprovedParentalConsent()` in [`src/lib/consent-check.ts:59-70`](../../src/lib/consent-check.ts) queries it with the uuid. Swapping in the Prisma id there silently returns "no consent" for every child, which closes the AI gate on the whole under-16 cohort.
2. **`app_user_id()` returns TEXT, not uuid.** [`supabase/migrations/20260421_00_app_user_id_fn_text_return.sql`](../../supabase/migrations/20260421_00_app_user_id_fn_text_return.sql) redefines it to look the Prisma cuid up via `User.supabaseUserId = auth.uid()`. Every RLS policy on a Prisma-shaped table compares against that TEXT value. The original uuid-returning version threw `42883 operator does not exist: text = uuid` and left a migration half-applied.

Notes worth carrying:

- **`Subscription.userId` is `@unique`** ([`prisma/schema.prisma:369`](../../prisma/schema.prisma)). One row per person. A person can hold several live Stripe subscriptions at once - Pro and IELTS are sold separately - so the Prisma row cannot represent the real billing state. Neither can `profiles.subscription_status`, which is one text field per person. That is why [`src/lib/billing/duplicate-subscription-guard.ts`](../../src/lib/billing/duplicate-subscription-guard.ts) asks Stripe rather than either of our own stores, and refuses only a second subscription carrying the _same price_.
- **`free_allowance_usage` has no FK to `User`, on purpose.** Most accounts have no Prisma row, and the `ip` subject has no user at all, so an FK would fail to count exactly the accounts that matter. Deletion is wired explicitly into [`src/lib/data-retention.ts`](../../src/lib/data-retention.ts) instead of relying on cascade.
- **`rate_limit_counter` has no Prisma model at all.** It is created by [`supabase/migrations/20260918_rate_limit_counter.sql`](../../supabase/migrations/20260918_rate_limit_counter.sql) and reached only through `$queryRaw` / `$executeRaw` in [`src/lib/rate-limit.ts:621,653`](../../src/lib/rate-limit.ts). It exists because Redis is not configured in production and the Upstash limiter was silently falling back to a per-instance in-memory `Map`, which is no limit at all on serverless. Same reasoning produced `free_allowance_usage`.
- `@@map` appears 18 times, so half the models are snake_case in the database and PascalCase in the client. `MarkingSubmission` is `marking_submissions`; `WeeklyStudentDigest` and `MobileDevice` keep their PascalCase table names and therefore need double quotes in raw SQL.
- `WeeklyStudentDigest` is a purpose-built send ledger rather than a reuse of `WeeklyReport`, because `WeeklyReport` requires a non-null `parentId` and carries a report body, while the student digest goes to the student whether or not a parent is linked. It records only that a digest was sent, never its contents, and the `@@unique([studentId, weekStarting])` is the real idempotency guarantee - the cron's pre-check is only a fast path.

The consent one is the cautionary tale and the fix is worth reading in full. The self-serve signup flow wrote its token to `consent_tokens` while the parent-facing page resolved tokens against `parental_consents.consent_token`. Every guardian who clicked the emailed link saw "invalid or has already been used", and `checkParentalConsent()` only ever reads `parental_consents`, so even a successful approval could not have unblocked AI marking. `consent_tokens` is left in place for historic rows but application code no longer touches it.

## Erasure: what a delete actually touches

Worth understanding before you add a table that holds personal data, because the two halves are erased by two different mechanisms.

- The Prisma half is erased inside one transaction in `hardDeleteUser` ([`src/lib/data-retention.ts`](../../src/lib/data-retention.ts)). Most models cascade from `User`. Three do not and are handled explicitly: `AuditLog.userId` is nulled rather than deleted (entries are kept for compliance), `SafeguardingReport` rows survive if a retention hold applies, and `CookieConsent` has no `@relation` at all so it would otherwise orphan with a live `userId` and keep `ipHash` plus `userAgent` past the erasure.
- `free_allowance_usage` is deleted after the transaction, by hand, because it has no FK by design. Both the user subject and any IP subject must go.
- The Supabase half is erased by deleting the `auth.users` row, outside the Prisma transaction. `profiles` cascades from it, and the learner-facing tables cascade from `profiles`. Without that step the email, password hash, login history and MFA factors would remain indefinitely, which contradicts what the deletion email promises.

So: a new table keyed on the Supabase uuid with `ON DELETE CASCADE` needs nothing. A new table keyed on the Prisma cuid needs either a cascading relation or an explicit line in `hardDeleteUser`. A new table keyed on neither - a hashed or synthetic subject - needs an explicit line and a comment saying why there is no FK.

## Row Level Security

RLS is the only access control on the Supabase half. There is no application-level authorisation layer behind it for tables reached with the session client.

- **The service role bypasses RLS entirely.** `createServiceRoleClient()` ([`src/lib/supabase/server.ts:52`](../../src/lib/supabase/server.ts)) authenticates with `SUPABASE_SERVICE_ROLE_KEY`; policies do not constrain it. Any route that reaches for it is asserting its own authorisation, and must do so explicitly.
- **Prisma bypasses RLS too, by a different route.** It connects with the Postgres connection string in `DATABASE_URL`, not a Supabase API key, and that role is not subject to policies. The header of [`20260506_enable_rls_on_prisma_tables.sql`](../../supabase/migrations/20260506_enable_rls_on_prisma_tables.sql) describes this as "the Prisma client using `SUPABASE_SERVICE_ROLE_KEY`", which is not how Prisma connects; the conclusion it draws is nonetheless right.
- **18 Prisma-managed tables carry RLS with a service-role-only policy.** That migration turned RLS on for `AIFeedback`, `Assignment`, `AssignmentSubmission`, `AuditLog`, `Consent`, `CookieConsent`, `DataAccessRequest`, `Essay`, `HumanReviewRequest`, `ParentInvite`, `PrivacySettings`, `RenewalReminder`, `SafeguardingReport`, `Suggestion`, `User`, `WeeklyReport` and friends. With RLS on and no permissive policy, anon and authenticated PostgREST access is deny-all. `rate_limit_counter` and `free_allowance_usage` follow the same convention.
- **Real per-row policies exist on** `profiles`, `enrolments`, `module_progress`, `assessment_attempts`, `certificates`, `practice_sessions`, `courses`, `modules`, `quiz_questions`, the school tables, the affiliate tables, `parental_consents`, `Subscription`, `MobileDevice`, `OfflineEssayQueueItem`, the four `progress_*` tables and `progress_cefr`, and `marking_submissions`.
- **`marking_submissions` is where child work is protected by policy alone** ([`20260512_marking_submissions.sql:59-122`](../../supabase/migrations/20260512_marking_submissions.sql)): a student may SELECT only rows where `auth.uid() = student_id`; teachers see rows for classes they teach via `school_members`; school admins see their school. There is no second check in the route.
- **`parental_consents` is the other one.** It holds consent tokens, guardian email addresses and minor-student linkage. [`20260322_new_features.sql:55`](../../supabase/migrations/20260322_new_features.sql) created a policy named "Service role full access" as `FOR ALL USING (true)` with no role clause, which in fact granted every authenticated user read and write over every row. A token read out of that table grants parental approval with no further verification. [`20260419_drop_parental_consents_permissive_policy.sql`](../../supabase/migrations/20260419_drop_parental_consents_permissive_policy.sql) removes it. Note why the earlier attempt failed: `004_fix_school_rls.sql` tried to drop the same policy but sorts _before_ `20260322`, so the DROP ran before the CREATE and did nothing. Migration ordering here is lexical, and a fix that sorts earlier than the defect is a no-op.

If you add a table that holds pupil data, RLS deny-all plus a service-role route is the safe default. A policy named after the service role but written without `TO service_role` is the specific mistake to avoid.

`package.json:13` runs `prisma generate && node scripts/apply-migrations.mjs && next build`. **There is no `prisma migrate deploy` and no `prisma db push` anywhere in the build, the CI workflows or the scripts.** Adding a model to [`prisma/schema.prisma`](../../prisma/schema.prisma) therefore does not create the table on deploy. Either write the matching SQL into `supabase/migrations/` - which is what every recent model has done - or apply it by hand and accept that the drift checker will never see it. `BulkUploadJob` and `ielts_attempts` are in exactly that position: Prisma models with a `prisma/migrations/` entry and no Supabase migration. `ielts_attempts` writes are wrapped in a `try/catch` that returns `{ persisted: false, reason: 'db' }`, with the comment "Table not migrated yet", so a missing table there is invisible.

### The BASELINE_CUTOFF problem

`BASELINE_CUTOFF = '20260530'` at [`scripts/apply-migrations.mjs:42`](../../scripts/apply-migrations.mjs). On the first run, when the tracking table `_migrations_applied` does not yet exist, every file sorting before that key is **inserted into the tracker without being executed**. On 2026-05-30 that recorded 66 files in four seconds.

The intent was reasonable: those files predated the runner and had been applied by hand. The reality is that at least one of them never had been. `20260512_user_is_minor.sql` creates `profiles.is_minor`. The column did not exist. [`src/lib/identity/profiles.ts`](../../src/lib/identity/profiles.ts) names `is_minor` in its column list on every identity read, so every read returned Postgres error `42703`, the caller discarded the error, and `resolveAgeBand()` degraded to UNKNOWN for all 206 accounts - blocking every consent-gated AI route on a children's product for four months. The column was created on 2026-09-18, and `readIdentityProfile` now reports a failed query to Sentry with the marker `IDENTITY_PROFILE_READ_FAILED` rather than returning a bare null.

The rule this leaves you with: **`_migrations_applied` records an intention; `information_schema` records reality.** Verify against `information_schema`, never against the tracker.

## Dead, half-dead, and write-only

Say so in the code when you confirm one of these, because they all look live from the schema.

**Models defined but never written:** `HumanReviewRequest`, `Suggestion`, `AssignmentSubmission` (only counted), `OfflineEssayQueueItem` (zero references in `src/` of any kind - the double-hop offline queue described in its comment was never built).

**Tables written but never read:** `CookieConsent` is created by `api/consent/cookie` and deleted by retention, and nothing ever selects from it. `RevenueCatEvent` is an append-only journal, read only by the webhook's own idempotency probe.

**Tables neither read nor written by `src/`:** `analytics_snapshots`, `bulk_import_jobs`, `import_results`, `school_access_periods`, `consent_tokens`, `quiz_questions`, `affiliate_commission_defaults`. `quiz_questions` is the surprising one - it has RLS policies, an "enrolled users view questions" policy and a consolidation migration, and no application code touches it.

**Superseded but retained:** `markers.boards[]` (use `marker_board_access`), `affiliate_payouts` versus `affiliate_payout_batches` (both live, different code paths), the legacy `Pass/Merit/Distinction` values in the `certificates.grade` CHECK.

Two migrations are worth reading as examples of the class of bug that hides in a CHECK constraint. [`20260818_certificates_grade_check.sql`](../../supabase/migrations/20260818_certificates_grade_check.sql): `001` constrained `grade` to `('Pass','Merit','Distinction')` while `/api/certificates` had always written `'Grade 9'`..`'Grade 4'`, so every issuance violated the CHECK, the upsert returned 500, and no student who passed a final assessment ever received a certificate. [`20260818_school_members_student_role.sql`](../../supabase/migrations/20260818_school_members_student_role.sql): `role` was constrained to `('admin','head_of_department','teacher')` while five routes and the bulk import write `role='student'`, so a school that imported hundreds of pupils reported zero students. Both fixes drop the constraint **by inspecting its definition** rather than by assuming its auto-generated name, because a half-applied fix that adds a second CHECK alongside the old narrow one is worse than no fix.

## If you are changing the schema

1. **Check the live schema first, not the migration history.** Run the drift checker. If the thing you are about to add already half-exists, adding a second definition is how you get two CHECK constraints with one auto-generated name each.
2. **Write the SQL into [`supabase/migrations/`](../../supabase/migrations/)**, named `YYYYMMDD_description.sql`. That directory is the only one the build applies. Adding a Prisma model without matching SQL ships a client that talks to a table nobody created.
3. **Make it idempotent.** Every file authored from `20260530` onward may be executed more than once: `CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, DO-block guards, drop-then-recreate for constraints and policies. Each file runs in its own transaction with its tracking row written inside it, so a failure leaves no "applied" record.
4. **Drop constraints by inspecting their definition, not by assuming their name.** The database has been hand-managed in places, so an auto-generated name you expect may not be the one that exists.
5. **Decide the key space explicitly and write it in a comment.** Supabase uuid for anything a learner reaches through the session client and RLS; Prisma cuid for anything the server owns. Do not mix them in one table without saying why, as `MarkingSubmission` does.
6. **Update [`prisma/schema.prisma`](../../prisma/schema.prisma) to match** if Prisma needs to see the table, and regenerate. The schema file is the client contract; it is not what creates the table.
7. **Add RLS.** Deny-all plus a service-role route is the safe default for anything holding pupil data. A policy named after the service role but written without `TO service_role` grants the whole table to every authenticated user.
8. **Wire deletion** into `hardDeleteUser` if the table does not cascade.
9. **Re-run the drift checker after deploy.** The tracker will say applied either way.

## Practical notes

- `DATABASE_URL` is in [`.env.example`](../../.env.example); `DIRECT_URL`, which [`prisma/schema.prisma:11`](../../prisma/schema.prisma) declares as the datasource `directUrl`, is not. I could not determine whether it is set in the deployed environment. The migration runner falls back through `MIGRATION_DATABASE_URL`, `POSTGRES_URL_NON_POOLING`, `DIRECT_URL`, `DATABASE_URL` and skips cleanly with exit 0 when none is set, so a local build without secrets does not fail - and does not migrate either.
- DDL runs on the direct, non-pooled connection on purpose. Pooled PgBouncer connections are unreliable for schema changes.
- The repo is public on GitHub. No customer data, no real email addresses, no tokens in migrations or in docs.
- Trust the code over the markdown. Most of the files at the repo root date from April and May 2026 and several contradict the current schema; [`supabase/migrations/README.md`](../../supabase/migrations/README.md) documents four of the eighty-one migrations and stops in March.
