# Architecture and code map

The English Hub is a single Next.js 15 App Router application on Vercel. One deployment serves the public marketing and revision site, four signed-in surfaces (student, teacher/school, parent, admin), a 199-route JSON API that an Expo mobile app also consumes, and fifteen scheduled cron endpoints. There is no second application of ours in the live request path: state lives in Supabase Postgres, money in Stripe, AI at Anthropic, and everything else is this repository.

Two facts in this chapter change how you read every other chapter. **Almost nothing on this site is statically rendered** - the build prerenders four routes out of 1,043 pages. And **[`src/middleware.ts`](../../src/middleware.ts) runs before every one of those renders, doing fourteen unrelated things in an order that is load-bearing**; an auth bypass in August 2026 came from getting that order wrong.

## How one request travels

Worth holding in your head before reading any route file, because six of these nine steps happen outside the file you are looking at.

1. **Vercel edge.** A platform-level domain redirect handles `www` before any of our code runs. Static assets under `_next/static` and the image extensions in the matcher never reach our middleware at all.
2. **[`src/middleware.ts`](../../src/middleware.ts)**, edge runtime. Fourteen steps, detailed below. It can 308, 307, rewrite, or refuse with JSON. If it continues, it has stamped `x-nonce` and `x-lang` on the **request** headers and a CSP on the response.
3. **`updateSession`** ([`src/lib/supabase/middleware.ts`](../../src/lib/supabase/middleware.ts)), called from inside step 2. Refreshes the Supabase session cookie, enforces forced password rotation, and applies the protected-route auth wall.
4. **[`src/app/layout.tsx`](../../src/app/layout.tsx)**, a server component. Reads `x-lang` and `x-nonce` from `headers()`, which is what makes the whole tree dynamic, sets `<html lang dir>` on first paint, and mounts the provider stack.
5. **The page.** Either a server component reading `@/lib/*` and `@/data/*` directly and `cookies()` through helpers such as `getServerBoard()`, or one of the 443 client pages that renders a shell and then fetches `/api/*`.
6. **Client hydration.** `SupabaseProvider` calls `getUser()` and loads the profile into `useAuthStore`; `useBoardStore` rehydrates from localStorage and reconciles against the cookie; `useT()` loads only the active locale's message map.
7. **API calls** land on `src/app/api/**/route.ts`, which have already passed the CSRF origin gate in step 2, then apply their own auth, entitlement, consent and rate-limit checks.
8. **Data.** Supabase PostgREST for most tables, Prisma for the cuid-keyed subset, Upstash Redis for rate limits, Stripe and Anthropic over HTTPS.
9. **Errors** go to Sentry through `sentry.server.config.ts` and the root `instrumentation-client.ts` (browser), each with its own PII scrubber. Note that [`src/instrumentation.ts`](../../src/instrumentation.ts) imports `../sentry.server.config` in **both** branches - line 3 under `NEXT_RUNTIME === 'nodejs'` and line 22 under `'edge'`. `sentry.edge.config.ts` exists, duplicates the scrubbers, and is imported by nothing, so editing it has no runtime effect. Chapter 10 covers this at length.

## The build

```
npm run build
  = prisma generate
  && node scripts/apply-migrations.mjs
  && NODE_OPTIONS='--max-old-space-size=14336' next build
```

That is [`package.json:13`](../../package.json). `next build` also fires the `prebuild` hook at [`package.json:12`](../../package.json), six generators in sequence:

| Step | Script                          | Produces                               | Blocks the build                                                                      |
| ---- | ------------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------- |
| 1    | `check-mdx-compile.mjs`         | nothing                                | Yes - added after 19 blog posts shipped with invalid MDX and rendered as empty shells |
| 2    | `generate-i18n-locales.mjs`     | `src/lib/i18n/generated/{en,ar,es}.ts` | Yes                                                                                   |
| 3    | `verify-i18n-locales.mjs`       | nothing                                | Yes                                                                                   |
| 4    | `generate-sitemap-routes.mjs`   | `src/lib/seo/static-routes.json`       | Yes                                                                                   |
| 5    | `generate-text-subpage-map.mjs` | text subpage map                       | Yes                                                                                   |
| 6    | `generate-llms-txt.mjs`         | `public/llms.txt`                      | Yes                                                                                   |

Steps 2 and 4 write files that are also **committed**, because `npm run dev` does not run `prebuild`. A locale key added without regenerating renders as `[[key]]` locally. Check `git diff --stat src/lib/i18n/generated/` before committing: a failed formatting step turns a three-line change into a 110,000-line diff.

**The 14 GB heap.** 14336 MB is not superstition, but I could not find the build that first ran out of memory, and the two guides in `business-docs/` still say 8192, so treat those as stale. The mechanism is visible in the tree: webpack compiles 1,248 app route entries in one process, and the module graph pulls in `src/data` (34 MB of TypeScript literals), the 1.5 MB `src/lib/i18n/dictionary.ts`, and the 4.5 MB of generated locale maps. On Windows the inline `NODE_OPTIONS='...'` syntax fails; use `export NODE_OPTIONS=--max-old-space-size=14336 && npx next build`. Do not "fix" the script - Vercel builds on Linux. I could not verify the Vercel build machine's RAM from anything in this repo; [`vercel.json`](../../vercel.json) does not select one, and asking for a 14 GB heap on an 8 GB box does not create memory, it only defers garbage collection until the OS kills the process.

**`scripts/apply-migrations.mjs` runs on every deploy** and has `BASELINE_CUTOFF = '20260530'` at [line 42](../../scripts/apply-migrations.mjs). Every migration file sorting before that string is INSERTed into `_migrations_applied` **without being executed**. The tracker records an intention, not reality. Verify schema against `information_schema`; [`scripts/check-schema-drift.mjs`](../../scripts/check-schema-drift.mjs) does exactly that and still finds real drift. Its header docblock is the best short account in the repo of the four-month `profiles.is_minor` outage.

CI ([`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) and [`deploy.yml`](../../.github/workflows/deploy.yml)) runs `npx next lint`, `npx tsc --noEmit`, `npm test` and `npm audit --omit=dev --audit-level=critical` as a gate before the Vercel deploy action. The EAL duplicate-body check is deliberately non-blocking (`|| true`).

## next.config.js

[`next.config.js`](../../next.config.js) is 230 lines and mostly comments explaining decisions. The parts that matter:

- **`typescript.ignoreBuildErrors: false`** ([line 13](../../next.config.js)). Type errors do fail the build. This was flipped back on when the project moved to Vercel Pro.
- **`eslint.ignoreDuringBuilds: true`** ([line 18](../../next.config.js)). Lint does not run in the build. The stated reason is that `@typescript-eslint` rules fail on test files, and [`.eslintrc.json`](../../.eslintrc.json) is consistent with that - it registers the plugin but never extends its recommended config. CI genuinely does run `npx next lint` separately, so the comment is accurate, but a deploy triggered from the Vercel dashboard rather than the GitHub workflow is unlinted.
- **`redirects()`** ([line 53](../../next.config.js)). Twenty permanent 308s; 21 entries in the compiled `routes-manifest.json` once Next's own trailing-slash rule is counted. Four groups: the May 2026 institutional repositioning (`/for-*` to `/schools`, `/teachers`, `/students`, `/school-pilot`), blog de-duplication after a scaled-content clean-up, `syllabus` URL flattening, and legal-page consolidation. **These redirects shadow live page files.** `src/app/for-schools/page.tsx` is 1,540 lines, `for-teachers/page.tsx` 1,289, `for-students/page.tsx` 302, and none of them can ever render, because a `next.config` redirect is evaluated before routing. Their _sub_-routes (`/for-schools/contact`, `/for-schools/register`, `/for-teachers/free-resources`) are not redirected and are still live. Same trap at `src/app/privacy-policy/page.tsx` and `src/app/legal/safeguarding/page.tsx`.
- **`headers()`** ([line 196](../../next.config.js)). Static security headers for `/(.*)`: X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy, COOP, CORP, HSTS. **Content-Security-Policy is deliberately absent here** and is set per request in the middleware, because a static header cannot carry a per-response nonce.
- **`images.remotePatterns`** allows exactly one external host, the Supabase storage domain.
- **`experimental.optimizePackageImports`** lists 14 barrel-heavy packages. Removing entries will inflate shared chunks measurably; the list was tuned against a bundle analysis.
- **`module.exports = withBundleAnalyzer(withSentryConfig(nextConfig, {...}))`** ([line 223](../../next.config.js)). Note `disableServerWebpackPlugin: process.env.VERCEL === '1'` and the same for the client plugin: **on Vercel the Sentry webpack plugins do not run**, so the build does not upload source maps. `npm run sentry:sourcemaps` exists for that and is not wired into the deploy. `ANALYZE=true npm run build` turns the analyzer on.

## Rendering model: dynamic by default, and not by accident

Evidence, from the committed build in `.next/prerender-manifest.json` and `.next/routes-manifest.json`:

| Category                                    | Count                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------ |
| App route entries                           | 1,248                                                                          |
| `page.tsx` files                            | 1,043                                                                          |
| `route.ts` handlers                         | 200 (199 under `src/app/api`, plus `src/app/auth/callback`)                    |
| **Prerendered at build time**               | **4** (`/icon.svg`, `/robots.txt`, `/sitemap.xml`, `/api/analytics/aggregate`) |
| ISR dynamic routes                          | 1 (`/analysis/[...slug]`, 24 h revalidate)                                     |
| Files declaring `dynamic = 'force-dynamic'` | about 125                                                                      |

Everything else is server-rendered per request. The cause is one line: [`src/app/layout.tsx:138`](../../src/app/layout.tsx) awaits `headers()` to read the `x-lang` and `x-nonce` values the middleware stamped. Reading request headers in the root layout opts the entire tree into dynamic rendering. That is the price of cookie-and-URL-driven trilingual rendering with a per-request CSP, and it was chosen knowingly, but it means Vercel serves this site as roughly a thousand server functions rather than as a CDN-cached static site. Any "why is TTFB high" investigation starts here.

The exceptions are instructive:

- **[`src/app/analysis/[...slug]/page.tsx`](../../src/app/analysis/%5B...slug%5D/page.tsx)** sets `revalidate = 86400`, `dynamic = 'force-static'` and `dynamicParams = true`. Because it is static, `headers()` is unavailable at render, so it cannot receive a CSP nonce. The middleware compensates by SHA-256 hashing that route's three JSON-LD bodies and appending `'sha256-...'` sources to `script-src` (`computeJsonLdHashes` in [`src/lib/seo/json-ld-hashes.ts`](../../src/lib/seo/json-ld-hashes.ts)). `t()` in [`src/lib/i18n/t.ts`](../../src/lib/i18n/t.ts) catches the `headers()` throw and falls back to English for exactly this case.
- **[`src/app/blog/[slug]/page.tsx`](../../src/app/blog/%5Bslug%5D/page.tsx)** compiles MDX per request via `next-mdx-remote/rsc`. Its header docblock (lines 18-39) is the honest version and worth reading in full: `dynamicParams = false` is meaningless on a dynamic route, where it stamped HTTP 200 on the not-found shell, so the route checks the slug against the catalogue and calls `notFound()` instead; and a post that fails MDX compilation throws per request and collapses to an empty shell **without failing the build**, which is how 19 posts shipped broken until August 2026.
- Ten routes declare `generateStaticParams` (KS3 year/term/week, revision texts, model essays, lesson plans, printables, courses). Under the dynamic root layout these currently buy route-shape knowledge rather than prerendering.

**Server versus client components.** 443 of the 1,043 pages carry `'use client'` at the top, so slightly over half the site's pages are client components whose data arrives by `fetch()` to `/api/*` from a `useEffect`, not through server-component data loading. The rest are server components importing from `@/lib/*` and `@/data/*` directly. Only three layouts are client components; the root layout is a server component wrapping a client shell ([`RootLayoutShell`](../../src/components/layout/root-layout-shell.tsx)), which is what lets the header and footer be hidden on `/school` and `/demo/school` without a route group. There are **no route groups, no parallel routes and no intercepting routes** anywhere in `src/app`. The tree is plain nested folders, which is the main reason a 1,043-page router is still navigable.

**Runtime.** Almost everything runs on Node. Only three route handlers declare `runtime = 'edge'`; 17 declare `runtime = 'nodejs'` explicitly and the rest inherit it. The middleware runs on the edge runtime, which is why it uses Web Crypto rather than `node:crypto` ([`src/middleware.ts:8-11`](../../src/middleware.ts)). [`vercel.json`](../../vercel.json) pins the region to `lhr1` and gives every `src/app/api/**` function a 60-second `maxDuration`, which matters because AI marking calls are slow.

## The API surface and the crons

199 route handlers under [`src/app/api`](../../src/app/api), across 51 top-level groups. (The repo has 200 `route.ts` files; the extra one is `src/app/auth/callback/route.ts`, the OAuth callback, which sits outside the API tree.) The distribution tells you where the complexity sits:

| Group                                                         | Routes   | What it is                                                                                                                                               |
| ------------------------------------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `school`                                                      | 47       | Classes, members, assignments, invites, join codes, CSV import, bulk upload. By far the largest surface, and the one with the most privileged operations |
| `admin`                                                       | 29       | Site admin, marker batches, user administration                                                                                                          |
| `cron`                                                        | 15       | See below                                                                                                                                                |
| `marker`, `marking`, `progress`, `ielts`, `auth`, `affiliate` | 6-7 each |                                                                                                                                                          |
| `stripe`, `privacy`, `parent`                                 | 4 each   | `stripe/webhook` is the billing entry point                                                                                                              |
| `me`, `dsar`, `consent`                                       | 3 each   | `/api/me` is the mobile app's session bootstrap and embeds the feature flags                                                                             |
| everything else                                               | 1-2 each |                                                                                                                                                          |

The fifteen cron paths in [`vercel.json`](../../vercel.json) each have a matching handler under `src/app/api/cron/`, with no orphans in either direction - a rare thing here, and worth preserving when you add one. Every handler authenticates on `CRON_SECRET`, but not uniformly, and **fourteen of the fifteen** report through `runCron` in [`src/lib/cron/observability.ts`](../../src/lib/cron/observability.ts). The exception is `trustpilot-retention-invite`, which authenticates inline, reads `x-cron-secret` before falling back to `Authorization: Bearer`, and returns its own response - so its failures leave no trace in the place you would look for them.

[`src/lib/cron/auth.ts`](../../src/lib/cron/auth.ts) was added on 17 September 2026 to consolidate this, and its docblock records why: `trustpilot-followup-7d` and `trustpilot-retention-90d` exported only `POST` while reading only `x-cron-secret`, so **every scheduled run since 19 April 2026 was answered 405 and nothing was sent** - invisibly, because a 405 never enters the `runCron` wrapper. Three other routes called `timingSafeEqual` without a length check, turning a wrong-length secret into a 500. If you want one example of this repo's failure mode, that is it. They fall into four families: trials (`trial-expiry`, `trial-ending`), retention and dormancy (`data-retention`, `dormancy-check`, `dormancy-purge`, `expire-invites`, `school-access`), reporting (`weekly-student-reports`, `weekly-parent-reports`), and growth (`affiliate-confirm`, `affiliate-confirm-v2`, three `trustpilot-*` jobs, `blog-generate`).

Two of those deserve a note. **`affiliate-confirm` and `affiliate-confirm-v2` are both scheduled daily and both are meant to be**: the v1 job works the legacy `affiliate_referrals` table, and v2 was added on 2026-05-03 because rows in the newer `affiliate_conversions` table sat at `status='pending'` forever and the dashboard's all-time earnings showed zero after a real sale. Deleting the one that looks redundant will break one of the two tables. And `trial-expiry` and `trustpilot-retention-90d` are both scheduled at `15 4 * * *`; they are unrelated jobs but they contend for the same minute.

The retention and dormancy crons are the ones a regulator would read. Treat their schedules as compliance artefacts, not as configuration.

**The `/ar` bypass, and why step 10 looks redundant.** Until 2026-08-23 the `/ar` branch returned the rewrite without ever calling `updateSession`, so `/ar/dashboard`, `/ar/account`, `/ar/school` and `/ar/admin` were reachable simply by prefixing a URL: no session refresh, no forced-password-rotation gate, no protected-route redirect. The fix is the pair at [lines 587-597](../../src/middleware.ts) - call `updateSession` against the **stripped** path (the raw `/ar/dashboard` would not have matched `/dashboard` in the protected list anyway), return its redirect if it produced one, and otherwise copy its refreshed auth cookies onto the rewrite response, because a token refresh performed during this request is otherwise lost and the next request looks unauthenticated. Any future locale branch must copy all four moves. The long comment at [lines 33-72](../../src/middleware.ts) explaining why there is deliberately no `/es` URL surface is the clearest statement of that contract in the codebase.

Note that [`src/lib/supabase/middleware.ts:122-126`](../../src/lib/supabase/middleware.ts) still carries a "KNOWN LIMITS" comment asserting that nothing in `updateSession` runs on the Arabic surface. **That comment is now false** - it describes the pre-fix state. Fix or delete it before it convinces someone the hole is still open.

**Two ordering consequences that are easy to miss.** Steps 5 to 8 test the raw `pathname`, and the `/ar` prefix is not stripped until step 10:

1. `/dashboard` is the one path the board gate still redirects, so an anonymous visitor with no board cookie hitting `/dashboard` is sent to `/board-select` at step 8 and never reaches the auth wall at step 11. **Board choice comes before sign-in.**
2. Because the raw pathname is tested, `/ar/dashboard` does not match either, so an Arabic visitor skips that redirect entirely. That is the only place the allow-list leaves a real English-versus-Arabic asymmetry - the other eleven prefixes are allow-listed for everybody.

**The nonce that is not a nonce.** `buildCsp()` at [line 292](../../src/middleware.ts) takes a `nonce` parameter and immediately discards it (`void nonce`). On 2026-05-02 the `'nonce-...'` source was dropped from `script-src` because Next 15.5 with React 19 stopped stamping `x-nonce` onto framework chunks: a rolled-back production deployment showed 0 nonce attributes against 96 on the green one, and because modern browsers ignore `'unsafe-inline'` whenever a nonce is present on the same directive, every framework chunk was blocked. Scripts now run under `'self' 'unsafe-inline'` plus an explicit host allow-list. The nonce is still generated, still stamped on request and response, and still read by `layout.tsx`, so a reader can easily conclude the site has nonce-based CSP when it does not. `'strict-dynamic'` was evaluated and rejected over iOS Safari 15.6 bugs. The August 2026 discovery that Trustpilot, Rewardful and Cloudflare Insights were live in the page but silently blocked by a stale `script-src` is recorded in the same comment block: if a third-party script "loads but does nothing", check `script-src` and `connect-src` here first.

**`updateSession` is where authentication actually happens** ([`src/lib/supabase/middleware.ts`](../../src/lib/supabase/middleware.ts)). Four things in it must stay as written. The `getAll`/`setAll` cookie wiring: the deprecated `get`/`set`/`remove` triplet mishandled chunked session cookies and was the suspected cause of intermittent "logged out after sign-in". `getUser()` must stay immediately after `createServerClient()`, because the Supabase client initialises lazily and anything in between risks the session being committed after the response is sent. The forced-password-rotation gate at [line 127](../../src/lib/supabase/middleware.ts) runs before the protected-route rule so it wins over every post-login destination - it holds bulk-provisioned school pupils on `/auth/set-password`, and its own docblock is honest that `user_metadata` is self-writable so this is a UI gate, not an access control. And `protectedRoutes` at [line 170](../../src/lib/supabase/middleware.ts) is matched segment-aware, because a bare `startsWith('/school')` once auth-walled the public `/schools` and `/school-pilot` marketing pages against Googlebot. `/revision`, `/practice`, `/learn` and `/games` are deliberately **not** protected so they stay crawlable; the paid actions inside them are gated server-side instead.

## What differs when you run it locally

`npm run dev` is plain `next dev`. Five things are not the same as production, and each has caught someone out.

- **`prebuild` does not run.** The generated i18n maps, `static-routes.json`, the text subpage map and `llms.txt` are whatever is committed. A new dictionary key renders as `[[key]]` until you run `npm run i18n:generate`.
- **`.env.local` is production.** It carries the production Supabase project URL - the same host allow-listed in `next.config.js` `images.remotePatterns` - and the **service-role key**, so RLS does not apply to anything you run locally, including ad-hoc scripts. Stripe is the one exception: only a `sk_test_` key is present. Grep any script in `scripts/` for writes before running it; `scripts/seed.ts` would put an admin account with a published password into the live database.
- **Sentry is off.** Every `Sentry.init` in this repo is guarded by `NODE_ENV === 'production'` plus a DSN, so nothing is reported in dev and nothing proves the scrubbers work.
- **`validateEnv()` logs, it does not throw.** [`src/instrumentation.ts`](../../src/instrumentation.ts) deliberately catches its own env validation and reports to Sentry rather than failing boot, on the reasoning that one missing variable should not take the site down. The consequence is that a deploy missing, say, `STRIPE_WEBHOOK_SECRET` boots clean and fails later, at the worst moment. This is the house pattern: things here fail and report success. When you add a guard, ask what it would report if the thing it guards were entirely absent.
- **`npm run build` fails on Windows** because of the POSIX inline `NODE_OPTIONS` syntax. Use `export NODE_OPTIONS=--max-old-space-size=14336 && npx next build`. Never pipe a build to `tail` and read `$?`; you get tail's exit code, not the build's.

**There is almost no pre-commit gate, whatever the convention says.** [`.husky/pre-commit`](../../.husky/pre-commit) is two commands: `node scripts/check-placeholders.mjs || exit 1`, then `npx lint-staged` (which is `eslint --fix` and `prettier --write` on staged files, per the `lint-staged` block in [`package.json`](../../package.json)). That is all of it. `npx tsc --noEmit`, `npx vitest run` and `node scripts/verify-i18n-locales.mjs` are a convention written down in [`CLAUDE.md`](../../CLAUDE.md) that you must run by hand - nothing blocks a commit that fails them. CI runs `npx tsc --noEmit` and `npm test` ([`.github/workflows/ci.yml:26-37`](../../.github/workflows/ci.yml)) and the `prebuild` chain runs `verify-i18n-locales.mjs`, so both are caught eventually, but only after the push. Given this chapter's own thesis, assume broken types and failing tests can and do reach `main`.

The 133 vitest suites run in about ten seconds and mock every database call, so they tell you nothing about whether the database agrees with the code.

## Seams: where you could cut

- **Content is already separable.** `src/data` is pure exported literals behind two lazy loaders, [`course-loader.ts`](../../src/data/course-loader.ts) and [`mock-exam-loader.ts`](../../src/data/mock-exam-loader.ts), both using `import()` against **leaf** modules. Read the defect note at the top of `mock-exam-loader.ts`: a previous version imported the aggregator, so the "lazy" chunk was the whole 2.8 MB paper set and the saving was zero. Listing UI must use `loadCourseIndex()` or `MOCK_EXAM_INDEX`, never `loadAllCourses()`. Moving this corpus into a database or CMS would cut the build's memory problem at source and change little else.
- **i18n is already a generated artefact.** The shards in `src/lib/i18n/dictionary-*.ts` are hand-written inputs; `generated/{en,ar,es}.ts` are outputs of a real compile-and-evaluate of the production resolver, so shard precedence cannot drift into a second implementation. Swapping in a translation service means replacing the generator, not the call sites - `t()` server-side, `useT()` client-side. The generator exists because `useT()` previously pulled the whole trilingual dictionary into every route's client graph: one shared chunk of 3.8 MB raw, referenced by 1,237 of 1,238 page manifests.
- **Auth is a thin membrane.** Every server entry point goes through `createServerSupabaseClient()` or `createServiceRoleClient()` in [`src/lib/supabase/server.ts`](../../src/lib/supabase/server.ts), and every request through `updateSession`. Note the comment there: `createServerSupabaseClient()` stays synchronous via `UnsafeUnwrappedCookies` and must become `async`, with every caller awaiting it, when Next 16 cache components land.
- **The API is a genuine boundary.** The Expo client consumes it over HTTPS with no shared code. Response shapes go through [`src/lib/api-response.ts`](../../src/lib/api-response.ts); note that 403 covers at least four distinct states (not a subscriber, no AI-processing consent, no guardian consent, AI switched off) and clients must switch on the `code` in the body, never on the status alone.
- **The board system is one registry.** [`gated-paths.ts`](../../src/lib/board/gated-paths.ts) is a deny-list feeding both the middleware gate and the `BoardGate` modal. It was deliberately inverted from an allow-list after `/blog` (the main organic entry point) and `/ielts` ended up behind a full-screen "pick your exam board" modal with no close button and no correct answer for an IELTS learner. Add a board-specific tree there and both consumers update together.

The seams that do **not** exist are worth naming too. There is no service layer between route handlers and `src/lib`, no dependency injection, and no repository pattern: route handlers call Supabase directly and frequently reimplement the same guard. That is why the invariants in `src/__tests__` - particularly `identity-guard.test.ts`, which forbids a second identity resolver - are doing structural work the type system is not.
